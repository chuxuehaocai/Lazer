# HiFi 队列所有权与 ABI 31 审计记录（2026-11-19）

审计对象：`codex/hifi-multiplatform-acceptance-20261119` 上本次改动（native preparation barrier、
ABI 31 精确清理、Dart 代次与 reader 所有权、测试与探针、文档）。
三轮审计在修复与第一轮测试之后进行，每轮都给出发现、严重级别、证据、修复、回归测试与残余风险。

验证环境：Windows 11 26300，MSVC 14.44，FFmpeg SDK `build/ffmpeg-sdk`，Dart/Flutter（本地）。
探针与 ctest 运行于 `build/native-probes`，Flutter 测试运行于仓库根目录。

## 第一轮：native 所有权与并发

检查项：准备屏障的锁顺序；wait 是否持有 `lifecycleMutex_`/`sourceMutex_`；
stop/open/retire/exact clear/destroy 是否完整等待；reader 回调是否可能晚于 Ok；
active/installed/preparing 三态转换；旧 API 语义；是否误清更新的后继；`sessionGeneration_` 是否阻止旧准备发布。

| 发现 | 严重级别 | 证据 | 修复 | 回归测试 | 残余风险 |
| --- | --- | --- | --- | --- | --- |
| 准备线程在锁外调用 `openReader()`，退场时直接 `source.close()`；并发 stop/clear 可能在探针仍持有 reader 时关闭它，导致 reader 回调晚于控制调用返回 | 高 | `Engine::queueReader` 原实现在释放 `lifecycleMutex_` 后调用 `openReader`，失败路径直接 `prepared->source.close()`；`Engine::open` 同样在锁外探测 | 引入 `SourceSlot` preparation barrier（`beginPreparation`/`requestPreparationCancel`/`finishPreparation`/`waitForPreparation`），准备线程只清 in-flight 并 notify，关闭一律由等待方在 wait 返回后执行；`closeSource()` 用 CAS 保证只关闭一次 | `runGatedCancellationCase(false/true)`、`runBlockedOpenCancellationCase()` | 未在真实 USB DAC 上观察取消时序，只有探针与测试替身证据 |
| 精确清理在 preparing 分支只把 `preparingSource_` 移出（WIP 遗留），既不 cancel 也不 wait，返回值 Ok 时 reader 仍可能被回调 | 高 | WIP 的 `clearQueuedReaderEx` 中 `matchesPreparing` 分支仅 `std::move` | 先在 `sourceMutex_` 下摘除 `preparingSource_`，再在锁外 `requestPreparationCancel()` + `cancel()` + `waitForPreparation()` + `joinPrefetch()` + `closeSource()`，之后才返回 Cleared | `runExactClearCancelsPreparationCase()`、`exact clear cancels a blocked preparation` | 同上 |
| 旧 API `clearQueuedReader` 被改写成委托给 `clearQueuedReaderEx(queueInstalledGeneration_, …)`，preparing 目标与 ErrorState 语义随之改变 | 中 | WIP 中 `clearQueuedReader` 只有一行转发；旧语义要求“无 installed successor 时返回 State” | 恢复独立实现：stale 不推进、advance 后按 installed（含 overlap 早退 AlreadyAudible）→preparing（比较推进前的请求代次）→active→默认 ErrorState，等待与关闭逻辑与屏障一致 | `clearQueued`/`stop`/`setQueue` 系列生命周期用例 | 旧调用方在 preparing 目标上仍会拿到 State，这是历史语义，未改 |
| 探针失败/取消后仍会发布或清理后继的状态字段：`pendingTrackChangedQueueGeneration_` 只写不读 | 中 | 该字段在 `tryStartQueuedSource` 中 3 处写入，全仓库无读取 | 删除字段与全部写入点 | 全量 Dart 测试与探针 | 无（纯冗余状态） |
| 退休路径（stop/open/替换/destroy）在持锁状态下等待准备线程会死锁：准备线程发布/放弃需要 `lifecycleMutex_` 与 `sourceMutex_` | 高 | `open()` 在 `lifecycleGuard` 下探测前需等待上一次会话的探针结束 | 退休改为两段：锁内把 slot 移入 `retiredSources_`，锁外 `reapRetiredSources()` 等待并关闭；`open()` 用 `RetireReaper` 保证每条返回路径都先解锁再回收 | `blocked open` 用例、`stop retires a preparation…` 用例 | 回收是串行的，理论上高并发 open 会排队；实测影响在毫秒级 |
| `queueReader` 在 `preparingSource_ != prepared`（被 clear 摘除）时只返回 ErrorState，未重置 `preparingSource_`，可能留下悬空发布状态 | 低 | 发布块只判断 `nextSource_ != nullptr` | 该分支补 `if (preparingSource_ == prepared) preparingSource_.reset();`，并在发布前检查 `preparationCancelled()` | `native superseded preparation returns false to its own append` | 无 |
| `sessionGeneration_` 复核缺失导致旧准备可能覆盖新会话 | 无（实现已存在） | `open()` 在重锁后比较 `sessionGeneration_ != generation \|\| cancelled_ \|\| !stillCurrent` | 保留复核，并把 stale 分支改为先 `finishPreparation()` 再返回 ErrorState，让等待方关闭 reader | 阻塞 open 用例 | 无 |

第一轮结论：所有 wait 点都在 `lifecycleMutex_`/`sourceMutex_` 之外（`reapRetiredSources`、两条 clear、`queueReader` 的 abandon 路径均先释放引擎锁）；
`~SourceSlot` 先 cancel/joinPrefetch 再 `closeSource()`；active/installed/preparing 三态转换没有出现在同一把锁内关闭 reader 的路径。

## 第二轮：Dart 代次状态机

检查项：source/request/resource generation 是否各司其职；worker 回包前、回包后、丢回包、延迟回包；
`_queuedReader == null` 时的 clear；URL/entry/reader 是否绑定到同一目标；四种返回值；stop/open/destroy 是否覆盖已提交 reader；
失败路径是否重复释放或泄漏。

| 发现 | 严重级别 | 证据 | 修复 | 回归测试 | 残余风险 |
| --- | --- | --- | --- | --- | --- |
| `_queuedSourceGeneration` / `_queuedQueueGeneration` 声明后从未赋值，`_retainQueuedReader` 用恒为 0 的代次建立延迟退休记录 | 高 | 两个字段只有声明与读取，没有任何写入点 | 在 `_prepareSuccessorImpl` 安装成功处写入真实 source/queue 代次；`_adoptActiveReader`/`_releaseQueued`/`_crossIntoSuccessor` 清零 | `native clear is ordered before an append invoked after it` 等 | 无 |
| 被取代的准备用新申请的全局代次调用**旧 API** 清理，没有目标参数，等于“丢掉此刻整支队列” | 高 | `_settleSupersededReader` 原实现 `++_queueGeneration` 后调 `clearQueuedReader(address, generation)` | 改为 `clearQueuedReaderEx(address, targetQueueGeneration, requestGeneration, preserveAudible: false)`，target 为该 reader 自己的 `queue_reader` 代次 | `native superseded preparation returns false to its own append`、探针 `runExactClearCancellationCase` | 旧引擎（ABI 30）走 loader 拒绝路径，不会进入该分支 |
| `ErrorState` 被当成“可以释放”的结果：清单元格之后立即 `reader.release()` | 高 | 原分支对 `lazerAudioErrorState` 与 Ok 同样处理 | ErrorState 改为 `_deferSupersededReader(...)`，reader 保持 leased 直到 stop/open/transition 确认；夹具同步改为不释放 | `State keeps a superseded reader until a transition confirms it` | 需要一次真实转移才会释放；若用户永不切换源，reader 存活到 destroy，属设计取舍 |
| `_clearQueued()` 只在 `_queuedReader != null` 时发 native 调用，无法取消仍在 worker 中排队的准备 | 高 | `final int hadQueued = _queuedReader == null ? 0 : 1;` 后才 RPC | 改为 `canCancel = _queuedReader != null \|\| _preparationsInFlight > 0 \|\| _pendingUrls.isNotEmpty \|\| _successorSlotUnconfirmed`，有在途准备就发 legacy clear 取消 | `stop retires a preparation that finishes after the request` | 空闲时不再发调用，减少一次无意义 RPC |
| 精确 clear 返回 ErrorState 后 successor 槽位仍被占用，下一次 `queue_reader` 被引擎按“第二个 successor”拒绝，append 返回 false | 中 | 夹具复现：`queue_reader` 返回 `lazerAudioErrorState` | `_successorSlotUnconfirmed` 守卫：准备队列轮到该任务时先清一次，再校验请求/源代次，失败则退出 | `native_queue_lifecycle_test` 全套 | 多清一次的代价是队列级 clear，不影响其他源 |
| stop 成功后再次发 clear（`_stopSource` + `_releaseQueued`），造成重复 RPC 与 `clearCalls` 断言偏移 | 低 | 测试断言 `clearCalls == 0` 实际为 1 | `_stopSource` 改为 `_confirmSourceTransition(generation, retiresGeneration: true)`，不再发第二次 clear | `stop releases an accepted successor without a second native clear` | 无 |
| 延迟退休的 reader 只在 destroy 时释放 | 中 | `_releaseDeferredReaders` 只挂在 `destroy` | `_confirmSourceTransition` 在 stop/open/install 后释放已确认的代次；stop 退休该代次本身，install 只退休更早代次 | `State keeps a superseded reader until a transition confirms it` | 无 |

第二轮结论：`_queueGeneration` 是唯一请求/目标代次计数器，`_generation` 是源代次，`_successorRequestGeneration` 记录当前准备的请求号；
三者在准备、回包、丢回包、延迟回包路径上分别校验；失败路径只走 `_retireOrHold` 与 `_deferSupersededReader`，没有再出现双重 release。

## 第三轮：平台、契约、测试与文档

检查项：ABI 31 在头文件/Dart mirror/worker/loader/导出映射/CI 是否一致；Windows/Android/Web 构建与导出检查；
iOS/macOS 是否只做契约同步；真实硬件证据是否与软件证据分开；文档是否残留过期 ABI；测试是否覆盖失败路径。

| 发现 | 严重级别 | 证据 | 修复 | 回归测试 | 残余风险 |
| --- | --- | --- | --- | --- | --- |
| 文档仍写 ABI 30 / 17 个必需符号 | 中 | `docs/audio-engine-status.md`、`docs/audio-engine.md`、`docs/audio-engine-hardware-verification.md`、`docs/ios-audio.md` | 统一为 ABI 31；必需符号 17→19；硬件验证文档的报错示例改为 `reports ABI 30; this build expects 31`；iOS 文档改为“ABI 30 引入的 13/14 枚举值” | `flutter analyze`、人工复核 | 交接手册中的 ABI 30 是历史记录，按“历史不可改写”保留 |
| 导出白名单未包含新符号，CI 会漏检 | 中 | `ci/verify-android-audio.py` 的 `ENGINE_EXPORTS`、`ci/verify-ios-audio.py` 的 `ABI_SYMBOLS`、`requiredEngineSymbols` | 三处均追加 `lazer_audio_clear_queued_reader_ex` | `flutter test native_audio_loader_test.dart`、APK 检查 | iOS 脚本不在本机能跑，只能静态核对 |
| Android 原生载荷无法在本机产出，`verify-android-audio.py` 报 missing payload | 中 | `ci/build-android-audio.sh` 仅支持 Linux/macOS；本机无 `build/android-ffmpeg` 与 `jniLibs` | 不改代码；改由 CI 的 Ubuntu job 产出并校验，本地记录 `hardwareTested=false` | `verify-package-contents.py` 通过 | 推送前无法本地证伪 Android 引擎 |
| 测试替身把 `ErrorState` 当作可释放，掩盖了 6.4 缺陷 | 高 | 夹具注释原写 “so the caller may release it” 并 `heldByNative.remove(context)` | 夹具改为 ErrorState 不释放，并新增 `freedWhileHeld` 断言 | `State keeps a superseded reader until a transition confirms it` | 无 |
| 测试替身允许并发 RPC，与真实单 isolate worker 不符 | 低 | 真实 `LazerWorker` 串行处理请求 | 夹具加串行 lane（`_lane`），复现真实排队顺序 | 全部生命周期用例 | 无 |
| 描述/注释仍把准备工作描述为“由准备线程关闭 source” | 低 | `engine.cpp` 屏障注释原文 | 改为“准备线程只清 flag 并 notify，等待方关闭，`closeSource()` CAS 保证一次” | 人工复核 | 无 |

第三轮结论：ABI 31 在头文件、Dart 常量、loader 绑定与必需符号表、worker op 14、两个 CI 脚本中一致；
Windows Release DLL 导出已用 `dumpbin` 复核；Web 通过条件导出回退到无 native 库的 stub；iOS/macOS 只改文档契约，没有新增能力；
真实硬件证据（第 2 节验收记录）与软件证据（探针、替身测试）分开陈述。

## 测试覆盖说明

失败路径覆盖：阻塞准备被 clear/stop 取消（探针 3 例 + Dart 3 例）、exact clear 代次陈旧与重复、目标不存在仍推进、
ErrorState 不释放、丢回包后具名清理、延迟回包被新队列取代、stop 与替换并发、旧引擎无 `_ex` 时的回退。

## 残余风险汇总

1. Windows 88.2/176.4/352.8 kHz 族被设备拒绝，未验证；DSD/DoP 与模拟回环未验证。
2. Android 引擎载荷与真机行为只有 CI 证据，本机 `hardwareTested=false`。
3. Linux 与 Web 没有运行证据。
4. 取消时序只有探针与测试替身证据，没有真实听感或长时观察。
5. `ErrorState` 后 reader 存活到下一次转移，是设计取舍，需在 PR 描述中说明。
